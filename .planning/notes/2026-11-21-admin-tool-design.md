# 러닝펜슬 관리도구 설계 (Admin Tool Design)

- 작성: 2026-11-21, 브레인스토밍 대화에서 정리
- 상태: 설계 초안 (사용자 승인 전)
- 만들어질 곳 (결정): 앱 저장소 `running_pencil`. 서버 쪽(관리자 함수·보안 규칙·숨김 상태)은 기존 `functions/`·`firestore.rules`에, 관리 웹 페이지는 새 폴더 `admin/`에 둔다. `admin/`은 관리 사이트만 다루는 자기 `firebase.json`을 갖고 그 폴더에서 `firebase deploy --only hosting:admin`으로 배포한다. 루트 `firebase.json`·`hosting/`은 Kit 소유 파일이라 건드리지 않는다(Kit 새 판 merge 충돌 방지). 함수는 다른 저장소·폴더에서 배포하지 않는다(앱 함수가 지워질 위험).
- 이 문서는 Phase 6 규칙(앱 저장소를 고치지 않음) 때문에 사이트 저장소 `.planning/notes/`에 임시로 둔다. 앱 쪽 작업을 시작할 때 앱 저장소 `docs/superpowers/specs/`로 옮긴다.
- 앱 저장소의 이전 설계 `.planning/notes/course-publication-quality-gate.md`(신고·자동 숨김)와 seed `SEED-261105-8ao`를 이어받는다. 겹치는 부분은 5.3의 결정을 따른다.

## 1. 왜 만드는가

출시 뒤 운영자가 자주 하게 될 일을 Firebase 콘솔을 직접 만지지 않고 안전하게 처리하기 위해서다. 지금 앱에는 「관리자」 개념이 없다(관리자 권한 claim도, 보안 규칙의 관리자 경로도 없음). 운영자가 할 수 있는 일은 콘솔에서 문서를 직접 고치는 것뿐이고, 이것은 실수하기 쉽고 누가 무엇을 했는지 남지 않는다.

사용자가 꼽은 가장 잦은 일 네 가지:

1. **완주 인정 처리** — GPS가 튀어 완주 판정이 안 났을 때, 운영자가 경로를 보고 인정한다.
2. **공개 코스 신고 처리** — 신고가 타당하면 코스를 숨긴다.
3. **삭제 요청 처리** — 앱을 탈퇴하지 않고 지운 사람이 메일로 보내는 삭제 요청.
4. **CS 이메일 처리** — 내용을 미리 알 수 없는 문의.

접수 통로(사용자 결정):

- **앱 안**: 대부분의 신고는 앱의 신고 버튼으로 받는다. 버튼이 대상 id(코스 id, 기록 id)를 함께 보내므로 처리가 쉽다.
- **메일**: 탈퇴 없이 앱을 지운 사람의 삭제 요청, 분류할 수 없는 CS 메일.

스토어 심사도 이 방향을 요구한다. Apple 가이드라인 1.2와 Google Play UGC 정책은 사용자가 만든 콘텐츠를 공개하는 앱(공개 코스가 해당)에 앱 안 신고, 신고에 제때 대응, 문제 사용자 차단을 요구한다. 그래서 앱 안 신고와 그 처리 수단은 출시에 필요한 기능이다.

## 2. 목표, 목표 아님, 실패 조건

**목표**

- 네 가지 일을 관리도구 화면에서 끝낸다. 콘솔을 열지 않는다.
- 권한이 필요한 모든 조치(숨김, 뱃지 부여, 삭제)는 서버 함수 한 곳을 거치고, 그 함수가 관리자 여부를 확인하고 기록을 남긴다.
- 앱 안 신고와 완주 인정 요청이 처리 대기 목록에 id와 함께 바로 보인다.

**목표 아님 (이번 범위 밖)**

- 통계·대시보드, 완주 판정 기준 조정 도구. (완주 인정 건수가 쌓이면 판정 기준이 너무 빡빡하다는 신호일 수 있다. 나중 일.)
- 메일함 기능. 메일 읽기·답장은 기존 메일함에서 한다.
- 만든 사람에게 앱 알림 보내기. 처음에는 메일 답장으로 알린다.
- 여러 운영자 간 권한 나누기.

**실패 조건 (돌아가도 실패로 보는 것)**

- 관리 코드나 관리 권한이 사용자 앱 안에 들어간다.
- 운영자가 사용자 위치기록(경로)을 열람했는데 그 사실이 남지 않는다.
- 숨긴 코스를 만든 사람이 스스로 다시 공개할 수 있다.
- 관리도구가 사용자 데이터를 외부 업체로 보낸다(처리방침에 없는 위탁이 생긴다).

## 3. 제약

- **runningpencil.com에 둘 수 없다.** GitHub Pages 공개 정적 사이트라 로그인·서버 처리가 없다. 관리도구는 Firebase 관리 권한이 필요하므로 앱의 Firebase 프로젝트 옆에 둔다.
- **환경이 셋이다.** 앱은 dev·stg·prod Firebase 프로젝트를 쓴다(`config/{dev,stg,prod}.json`, `hosting/build.mjs --project`). 관리도구도 세 환경에 같은 방식으로 배포된다.
- **기존 호스팅과 섞지 않는다.** 앱 저장소의 Firebase Hosting은 지금 인증 결과 페이지(`hosting/public`)를 서빙한다. 관리도구는 별도 호스팅 사이트(target)로 둔다.
- **주소 (결정):** prod 관리도구는 `admin.runningpencil.com`. `runningpencil.com/admin` 같은 경로형은 불가능하다(`runningpencil.com`은 GitHub Pages가 서빙하므로 경로 하나만 Firebase로 보낼 수 없다). dev·stg 관리도구는 Firebase 기본 주소(`<사이트 이름>.web.app`)를 써서 주소만 보고 환경을 구분한다(제안). DNS는 가비아에서 `admin` 레코드만 더하고 네임서버는 옮기지 않는다(사용자 작업). 기존 `runningpencil.com`(GitHub Pages)과 메일(MX)은 영향 없다.
- **본 사이트 호스팅 이전과는 별개다.** `runningpencil.com` 자체를 Firebase Hosting으로 옮기는 일은 ROADMAP 백로그 Phase 999.1로 다음 마일스톤에 한다. 관리도구 서브도메인은 이전 여부와 무관하게 동작한다.
- **위치정보법.** 운영자가 사용자의 `runs` 경로를 보는 것은 개인위치정보 이용에 해당할 수 있다. 위치정보 수집·이용·제공사실 확인자료 기록(Phase 6 요청서 ⑥, U2 결론에 따름)과 연결해야 한다.
- **사이트 문서와의 일치.** 신고 기능은 새 개인정보(신고자 uid, 신고 사유)를 만든다. 신고 기능이 나가는 시점에 데이터 목록(`DATA-INVENTORY.md`), 삭제 안내, 처리방침을 같은 시점에 고친다(아래 7절).
- **약관.** Google Play는 사용자가 콘텐츠를 올리기 전에 약관 동의를 요구하고, 심사자는 약관에 부적절한 콘텐츠를 허용하지 않는다는 문장이 있는지 본다. 이용약관(Phase 8)에 반영한다.

## 4. 만드는 방식 (Approaches)

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 별도 웹 관리 페이지 (선택)** | Firebase Hosting 별도 사이트 + 관리자 전용 서버 함수 + 네이버 지도 웹 API | 앱과 같은 프로젝트·배포 방식, 권한 검사와 기록이 서버 한 곳에 모임, 관리 코드가 사용자 앱에 들어가지 않음 | 웹 화면을 새로 만들어야 함 |
| B. Flutter 웹 관리 화면 | 앱 코드를 재사용해 웹으로 빌드 | 데이터 모델 재사용 | 앱이 쓰는 네이버 지도 Flutter 부품이 웹에서 도는지 확인 안 됨. 안 되면 경로 겹쳐 보기가 막힘 |
| C. 명령줄 스크립트부터 | 처음엔 스크립트만, 화면은 나중 | 가장 빠름 | 완주 인정은 경로를 눈으로 봐야 함. 매일 쓰기엔 실수가 쉬움 |

뺀 방식: Retool 같은 외부 관리 도구. 위치기록을 외부 업체에 넘기게 되어 처리방침에 위탁을 더해야 하고, 숨김·뱃지 같은 처리 규칙은 어차피 서버 함수로 만들어야 한다.

**사용자가 A를 골랐다.** 이유: Phase 6 앱 작업의 ③ 운영자 삭제 도구를 이 방식의 첫 서버 함수로 만들면, 출시 전에는 명령으로 부르고 나중에 관리 화면 버튼이 같은 함수를 부를 수 있다. 관문을 막지 않고 작업이 버려지지 않는다.

## 5. 정해진 설계

표기: **(결정)** 사용자가 정한 것, **(제안)** 대화에서 제가 제안했고 사용자가 반대하지 않은 것. 제안은 승인 때 다시 확인한다.

### 5.1 구성

- **관리 웹 페이지** — Firebase Hosting 별도 사이트(target). 화면만 그리고, 데이터 변경은 하지 않는다. (결정: 방식 A)
- **관리자 서버 함수** — 숨김/숨김 해제, 뱃지 부여, 계정 전체 삭제, 위치 기록만 삭제, 사용자·코스·기록 조회. 모든 함수는 호출자의 관리자 claim을 확인하고, 실패하면 거부한다. 조회 함수도 서버 함수를 거친다(경로 열람 기록을 남기기 위해). (제안)
- **관리자 표시** — Firebase Auth custom claim `admin: true`. 운영자 계정에만 명령으로 붙인다. 관리 페이지 로그인도 Firebase Auth를 쓴다. (제안)
- **운영 기록(audit log)** — 관리자 함수가 조치마다 한 건씩 남긴다: 누가, 언제, 무엇을(조치 종류), 어떤 대상(uid·코스 id·기록 id), 왜(연결된 신고·요청 id나 메모). 경로를 열람한 것도 한 건으로 남긴다. 사용자 앱에서는 읽을 수 없다. (제안)
  - **U2 결론 뒤 확정:** 경로 열람 기록이 위치정보 수집·이용·제공사실 확인자료(Phase 6 요청서 ⑥)에 해당하는지, 운영 기록 보존 기간, 탈퇴한 사용자의 uid를 운영 기록에 남겨도 되는지. ⑥은 탈퇴·위치 기록 삭제 때 확인자료를 지체 없이 파기하라고 하므로, 열람 기록이 확인자료라면 ⑥의 저장소에 두고 함께 파기되어야 한다. 처리방침(Phase 7)에 공개할 내용도 이 결론에 따른다.
- **App Check** — 앱의 서버 함수는 모두 App Check를 요구한다. 관리 페이지에도 웹용 App Check(reCAPTCHA Enterprise 등)를 붙인다. (제 판단)
- **쓰는 사람** — 당분간 운영자 한 명(사용자 본인). (제안)

### 5.2 화면

```
[처리 대기]  [찾기]  [운영 기록]
─────────────────────────────────────────────
처리 대기 (앱 안 접수)
  종류        대상            접수 시각    상태
  코스 신고    코스 「강아지런」  11-21 09:12  대기   → 열기
  완주 인정    기록 r_8f2…     11-21 08:40  대기   → 열기
```

- **처리 대기 목록** — 앱 안에서 들어온 코스 신고와 완주 인정 요청. 열면 대상 상세 화면으로 간다. 처리하면 상태가 「처리됨(조치)」 또는 「기각」으로 바뀐다. (제안)
- **찾기** — 이메일, uid, 코스 이름(+지역)으로 사용자·코스·기록을 찾는다. 메일로 온 일(삭제 요청, CS)의 출발점이다. (제안)
- **코스 상세** — 코스 선, 만든 사람, 공개 상태, 받은 신고 목록, 「숨기기」/「숨김 해제」 버튼.
- **완주 인정 화면** — 지도 한 장에 코스 선과 사용자 경로를 겹쳐 보여 주고 「인정」/「기각」 버튼. 화면을 여는 순간 경로 열람이 운영 기록에 남는다. (제안)
- **사용자 상세** — 계정 정보(로그인 제공자, 가입일), 기록·뱃지·코스 수, 「계정 전체 삭제」/「위치 기록만 삭제」 버튼. 삭제는 대상 uid를 한 번 더 입력해야 실행된다. (제안)
- **운영 기록** — 조치 이력 목록.

### 5.3 일별 처리 규칙

**완주 인정** (결정: 경로를 보고 인정)

- 근거 자료: 앱은 미완주 기록도 `runs`에 저장한다(앱 D-13). 운영자가 볼 경로가 이미 남아 있다.
- **인정 필드 (결정):** 앱은 완주 여부를 뱃지가 아니라 `runs.isCompleted`로 판단한다(`lib/features/runs/domain/completed_runs.dart` — 코스 카드 ✔, 완주 탭, 완주 수). 기록은 쓴 뒤 고칠 수 없다(rules `update: if false`, 앱 D-25). 그래서 `isCompleted`는 바꾸지 않고, 서버 함수가 기록에 인정 필드(예: `approvedAt`, `approvedBy`)를 더한다. 이 필드는 서버만 쓸 수 있다(클라이언트 rules는 계속 `update: if false`).
- 앱과 서버 쪽 집계(완주 표시, 완주 탭·수, 앞으로의 소급·개척자 뱃지 트리거)는 「`isCompleted` 또는 인정됨」을 완주로 읽도록 함께 바꾼다. `DATA-INVENTORY.md`의 `runs` 행에 새 필드를 더한다(신고 기능과 같은 시점, 7절).
- 인정하면 같은 서버 함수가 `users/{uid}/badges/{courseId}`도 만든다. `runId`는 그 기록, `earnedAt`은 실제로 달린 시각(기록 시각)으로 적는다. (제안: 사용자 입장에서는 그날 완주한 것)
- 이미 그 코스 뱃지가 있으면 뱃지는 만들지 않고 인정 필드만 더한다.
- 비공개 코스 기록은 대상이 아니다(앱은 비공개 코스엔 뱃지를 주지 않고 공개 때 소급한다, 앱 D-16). (제안)
- 운영자 인정이라는 사실은 인정 필드와 운영 기록에 남는다. 뱃지 화면에 따로 표시하지 않는다. (제안)

**공개 코스 신고** (결정: 숨김, 자동 숨김과 운영자 숨김 둘 다)

- 신고 데이터는 앱 이전 설계를 따른다: `courses/{id}/reports/{uid}` — 한 사람이 한 코스에 한 번만 신고한다. (결정: 이전 설계 이어받기)
- **자동 숨김:** 신고 수가 기준을 넘으면 서버가 코스를 숨김으로 바꾼다(이전 설계). 기준 수는 앱 쪽 설계에서 정한다.
- **운영자 숨김:** 기준에 못 미쳐도 운영자가 처리 대기 목록에서 바로 숨길 수 있다. 처리 대기 목록에는 신고가 들어온 모든 코스가 보이고, 자동 숨김된 코스는 「자동 숨김 — 확인 필요」로 맨 위에 보인다. (결정: 둘 다)
- 코스에 새 상태 「숨김(hidden)」을 더한다. 지금 상태는 `visibility`의 `private`·`public` 둘뿐이고, 다음 마일스톤에 검수 대기 `pending`이 예정되어 있다(rules·`course_repository.dart`에 교체 지점 표시). 숨김과 검수 대기는 같은 `visibility` 값 집합의 서로 다른 값이다. 공개 코스 목록은 이미 `visibility == 'public'`으로 거르므로 숨김은 자동으로 빠진다.
- 숨긴 코스는 목록·검색·지도에서 빠지고, 다른 사람이 새로 달릴 수 없다. (제안)
- 만든 사람에게는 「운영자가 숨김」 표시와 함께 계속 보이지만, 스스로 다시 공개할 수 없다. 지금 보안 규칙은 만든 사람이 `private → public`으로 바꿀 수 있게 열려 있으므로, 숨김 상태에서는 이 길과 다른 수정 길을 막아야 한다. (제안)
- 숨김 해제는 운영자만 한다(잘못된 신고 바로잡기). (제안)
- 이미 그 코스로 받은 다른 사람들의 뱃지는 그대로 둔다. (제안)
- 만든 사람은 숨겨진 코스를 삭제할 수 있다. 자기 데이터 삭제는 막지 않는다. 신고·조치 사실은 운영 기록에 남는다(U2 결론 뒤 확정 범위 안에서). (제 판단)
- 만든 사람에게는 처음엔 메일로 알린다. (제안)

**처리 대기 항목의 정리** (제 판단)

- 신고자가 탈퇴하면 그 사람의 신고(`courses/{id}/reports/{uid}`)를 지운다. 자동 숨김 판정에 쓴 수는 줄어들지만 이미 숨긴 코스는 그대로 둔다.
- 대상 코스나 기록이 지워지면 처리 대기 항목은 「대상 없음」으로 자동 종료한다.

**삭제 요청** (메일 접수)

- Phase 6 요청서 ③을 그대로 따른다: 운영자가 uid를 넣어 「계정 전체」(탈퇴와 같은 단계) 또는 「위치 기록만」을 실행한다.
- ③은 관리자 claim을 확인하는 서버 함수(callable)로 만든다. 출시 전에는 명령으로 부르고, 관리 화면의 버튼이 나중에 같은 함수를 부른다. 로컬 Admin SDK 스크립트로 만들지 않는다. (제 판단: 방식 A를 고른 이유)
- 「계정 전체」는 Auth 사용자 삭제가 기존 정리 트리거(`cleanup_user_data.ts`, Auth 삭제 이벤트)를 부르는 구조를 그대로 쓴다.
- 본인 확인과 답장 절차는 Phase 6 운영 절차서(06-05, `USER-TASKS.md` 작업 13)를 따른다. 관리도구는 「찾기 → 사용자 상세 → 삭제」 화면을 제공할 뿐 절차를 바꾸지 않는다.

**CS 이메일**

- 관리도구는 「찾기」로 계정과 기록을 보는 데만 쓴다. 답장은 메일함에서 한다.

## 6. 앱 쪽 선행 작업 (관리도구가 기대는 것)

관리도구가 쓸모 있으려면 앱에 아래가 먼저 있어야 한다. 이 묶음은 **Phase 6 앱 작업(①②③⑤⑥) 다음, 출시 전** 묶음으로 한다. (결정: 다음으로 미루기) 「출시에 필요」(1절)와 「다음 묶음」은 충돌하지 않는다. 이 묶음을 시작할 때 앱 REQUIREMENTS의 Out of Scope 「모더레이션·신고·차단」 항목을 다시 연다(앱 PROJECT D-05 전제 재검토). 이 문서의 범위는 관리도구이고, 이 묶음은 그 전에 따로 계획한다. prod·stg Firebase 환경 구성(지금은 dev만 있음)도 이 문서 범위 밖이다. (제 판단)

1. **앱 안 신고 버튼** — 공개 코스 화면에서 신고. `courses/{id}/reports/{uid}`에 신고 사유(선택 항목 + 선택 입력)와 접수 시각을 남긴다.
2. **완주 인정 요청 버튼** — 미완주 기록 화면에서 요청. 기록 id와 대상 코스 id를 함께 보낸다. (제안: 대화에서 「걷기의 id 같은 걸 같이 받는다」고 해서 이렇게 이해했다)
3. **숨김 상태** — 앱이 숨긴 코스를 목록·검색·지도에서 빼고, 만든 사람에게 「운영자가 숨김」 표시를 보인다. 보안 규칙 변경 포함.
4. **차단** — 스토어 요구(Apple 1.2, Google Play UGC). 러닝펜슬에서 차단이 무엇을 뜻하는지(예: 그 사람이 만든 코스를 내게서 안 보이게)는 앱 쪽 설계에서 정한다. 관리도구 범위 밖.

완주 인정 요청은 코스 신고와 별도 컬렉션에 쌓는다(대상이 기록이라 코스 하위에 둘 수 없다). 사용자 앱은 쓰기만 하고 남의 요청은 읽지 못하게 한다. 신고자·요청자 본인이 자기 신고·요청 상태를 볼 수 있게 할지는 앱 쪽 설계에서 정한다.

## 7. 사이트 문서와 맞출 것

신고 기능이 나가는 앱 버전과 **같은 시점에** 아래를 고친다. (결정: 다음 묶음으로 미루고 그때 함께 고침)

- `DATA-INVENTORY.md`에 신고·요청 데이터 행: 무엇을 남기는지, 보존 기간, 탈퇴 때 어떻게 하는지. `runs` 행에 인정 필드.
- `/data-deletion/` 삭제 안내: 탈퇴 때 신고 기록의 처리.
- 개인정보처리방침(Phase 7): 신고 데이터 항목, 운영자 경로 열람(이용 목적: 완주 인정·신고 처리).
- 이용약관(Phase 8): 부적절한 콘텐츠 금지, 신고·숨김·차단 조항.
- `/support/#report`: 「앱의 신고 버튼으로 신고하고, 앱을 쓸 수 없으면 메일로」로 바꾼다. 앵커 이름 `#report`는 그대로 둔다.
