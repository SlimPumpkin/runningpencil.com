**되돌릴 대상 (명시).**
- **`HISTORY_DECISION=base-first`: 커밋 정확히 두 개.** 02-01이 EVIDENCE에 적은 `HOOK_SHA`(scripts/check-site.sh, .githooks/pre-push)와 `BUILD_CONFIG_SHA`(Gemfile, Gemfile.lock, _config.yml, .gitignore)다. 이때 푸시 전 원격 main(`PUSH1_PREV`)은 02-02에서 라이브 확인을 통과한 기준 커밋이다. 범위 안에서 사이트 빌드나 출력에 영향을 줄 수 있는 커밋은 이 둘뿐이고, 나머지는 `.planning/` 기록 커밋이다. 두 커밋을 되돌린 트리는 `.planning/` 밖에서 기준 커밋과 같으므로 푸시 전 라이브 상태가 돌아온다.
- **`HISTORY_DECISION=together`: 이 푸시 범위 전체(`PUSH1_PREV..PUSH1_SHA`)를 한 번에.** 이 경우 범위에 Phase 1 이력 전체가 들어 있다. FAIL이 Phase 1에서 처음 원격에 들어간 내부 파일(`/.planning/…`, `/.claude/CLAUDE.md`)이 열리는 것이라면, 두 커밋만 되돌려서는 닫히지 않는다. 범위 전체를 되돌린 트리는 푸시 전 원격 main(`PUSH1_PREV`)의 트리와 똑같다. 그래서 원인이 무엇이든 푸시 전 라이브 상태를 정확히 되살린다. `02-02-PLAN.md`의 `<rollback_procedure>`와 같은 방식이다.
- 어느 경우든 범위 안의 커밋을 골라 일부만 되돌리지 않는다. 특히 exclude에 `.planning/`을 더한 Phase 1 커밋(7e0c426) 하나만 되돌리면 `.planning/`이 사이트로 공개된다. `git log "$PREV..$PUSHED" -- …` 꼴의 경로 선택으로 대상을 고르지 않는다.

**점검 도구는 메인 작업 트리에 그대로 둔다.** 되돌린 트리에는 Gemfile, Gemfile.lock, scripts/check-site.sh, .githooks/pre-push가 없다. 그래서 되돌리기는 저장소 밖 시험용 worktree에서 하고, 검증과 푸시는 메인 체크아웃에서 한다. 메인 체크아웃의 HEAD는 그대로 두므로 점검 도구와 훅이 남는다. `scripts/check-site.sh <커밋>`과 pre-push 훅은 메인 작업 트리의 도구로 그 커밋을 `git archive`로 내보내 빌드한다. 그래서 그 커밋에 Gemfile이 없어도 돈다. 02-02에서 기준 커밋을 점검할 때와 같은 방식이다.
1. 메인 체크아웃에서 EVIDENCE의 `HISTORY_DECISION`, `PUSH1_PREV`, `PUSH1_SHA`, `HOOK_SHA`, `BUILD_CONFIG_SHA`를 읽고, 해시는 전체 해시 `PREV`, `PUSHED`, `HK`, `BC`로 바꾼다. `RB_WT="$RP2/rollback"`로 둔다. 그 경로가 worktree 목록에 있으면 `git worktree remove --force "${RB_WT:?}"`로 지운다. 브랜치 `rp2-rollback`이 이미 있으면 멈추고 보고한다. `git worktree add -b rp2-rollback "$RB_WT" "$PUSHED"`로 만든다.
2. 되돌림 커밋을 만든다. 충돌이 나면 `git -C "$RB_WT" revert --abort` 뒤 멈추고 보고한다. 끝나면 `RB=$(git -C "$RB_WT" rev-parse HEAD)`로 둔다.
   - base-first: `git -C "$RB_WT" revert --no-edit "$HK" "$BC"`를 실행한다 (새 것부터).
   - together: `git rev-list --merges --count "$PREV..$PUSHED"`가 0인지 확인한다. 0이 아니면 멈추고 보고한다. `git -C "$RB_WT" revert --no-commit "$PREV..$PUSHED"`로 범위 전체를 새 것부터 되돌려 인덱스에 쌓고, `git -C "$RB_WT" commit -m "revert: 푸시 ① 범위 전체를 되돌림 (D-18)"`으로 커밋 하나를 만든다.
3. 메인 체크아웃에서 세 가지를 확인한다. 하나라도 실패하면 푸시하지 않고 멈춰서 보고한다.
   - `scripts/check-site.sh "$RB"`가 `check-site: 통과`를 출력한다.
   - `"$RP2/compare.sh" "$B" "$RB"`가 OK 5줄이다.
   - 트리 동일. base-first면 `git diff --quiet "$B" "$RB" -- . ':(exclude).planning'`이 0으로 끝난다 (되돌린 트리가 `.planning/` 밖에서 기준 커밋과 같다). together면 `git diff --quiet "$PREV" "$RB"`가 0으로 끝난다 (되돌린 트리가 푸시 전 원격 main과 같다).
4. **Task 3을 실패로 끝내고, 되돌리기 푸시는 따로 띄우는 `checkpoint:decision`으로만 승인받는다 (D-16).** Task 3은 `LIVE_PUSH1=OK`를 쓰지 않으므로 verify가 실패한다. 실행자는 FAIL 줄 전체와 1~3번 결과를 EVIDENCE의 `## 02-03 푸시 ① 라이브 확인` 구간에 적는다. 그다음 인증 게이트처럼 그 자리에서 `checkpoint:decision`(gate="blocking-human")을 만들어 멈춘다. auto task 안에서 말로 승인을 묻지 않는다. D-16이 푸시 승인을 단계 중간에 멈추는 `checkpoint:decision`으로 정했기 때문이다. checkpoint의 내용은 다음과 같다.
   - decision: 되돌림 커밋 RB(12자리를 문장에 적음)를 원격 main에 푸시할지 (main 푸시 = 라이브 배포)
   - context: FAIL 줄 전체, 되돌림 커밋, 함께 나갈 커밋 목록 `git log --oneline "$PUSHED..$RB"`, 3번 결과. together면 두 가지를 분명히 알린다. 이 되돌림은 원격 main 끝에서 `.planning/`·`.claude/`와 Phase 1의 `CLAUDE.md` 변경을 지운다(라이브 복구용이고, 공개된 이력은 그대로 남는다). FAIL이 내부 파일 노출이면 그 내용은 이미 공개 저장소에 있다.
   - options: `rollback-push`(RB를 푸시한다. 이 승인은 이 되돌리기 푸시 하나에만 쓰고, 앞뒤 어떤 푸시로도 이어지지 않는다), `other`(되돌리지 않고 다른 대응을 고른다. 그 결정을 EVIDENCE에 적고 멈춘다)
   - resume-signal: 「rollback-push」 또는 「other: <대응>」
5. 4번 checkpoint에서 `rollback-push`를 받은 뒤에만 이어서 실행한다. 메인 체크아웃에서 `git fetch -q origin main`을 실행해 원격 main이 `PUSHED` 그대로인지 확인한다. 그다음 `git push origin "$RB:refs/heads/main"`을 실행한다. git은 메인 작업 트리의 `.githooks/pre-push`를 부르고, 훅이 `$RB`를 점검한다. 훅이 실패하면 `--no-verify` 없이 멈추고 보고한다. 푸시 뒤 `"$RP2/live-check.sh" post "$RB"`로 복구를 확인하고, 출력을 EVIDENCE의 `## 02-03 푸시 ① 라이브 확인` 구간에 붙인다. 끝나면 `git worktree remove "${RB_WT:?}"`로 시험용 worktree를 지운다. 브랜치 `rp2-rollback`은 남긴다.
6. 로컬 main에 `rp2-rollback`을 합치는 일은 원인 수정 작업의 첫 단계로 미룬다. 되돌림 커밋을 그대로 합치면 메인 작업 트리에서 점검 도구와 훅이 사라지고, 그 상태로 푸시하면 점검 없이 나간다. 그래서 원인 수정 때는 먼저 `rp2-rollback` 위에서 되돌림 커밋(base-first는 둘, together는 하나)을 다시 `git revert`해 트리를 `PUSHED`와 같게 만든 뒤, 로컬 main에 `git merge --no-edit rp2-rollback`으로 합친다. 이 병합은 main의 트리를 바꾸지 않으므로 점검 도구와 훅이 계속 남는다. 그다음 원인을 고치고, 새 승인을 받아 훅 점검을 거쳐 푸시한다. 5번의 복구 확인에서도 FAIL이 남으면 원인이 되돌린 범위 밖에 있다는 뜻이다(base-first는 운영 환경이나 앞 단계 이력, together는 운영 환경). 그때는 더 되돌리지 않고 멈춰서 보고한다.
7. force push, `git reset`으로 원격 이력 고치기, `--no-verify`는 쓰지 않는다.
